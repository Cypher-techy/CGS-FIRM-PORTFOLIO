# Supabase production database deployment

`migrations/` is the single source of schema history. The first two versions contain the guarded fresh baseline and initial catalogue; the third hardens staff identity, records initial-owner provisioning and restricts its RPC to `service_role`. The historical `schema.sql` and `seed.sql` paths are **aliases**, not a parallel installation procedure. Do not run them individually. The CLI applies each file and records its version in a single transaction. Keep deployed migrations immutable. Add new timestamped forward migrations for changes. Local seed hooks are disabled to avoid seeding twice.

## One-time owner setup

1. Select the **dedicated corporate** Supabase project; confirm its ref, enable the public Data API and email/password provider, disable public signup, and back up before changes. Local `config.toml` is not pushed into hosted Auth settings.
2. Create the GitHub Environment **`production-database`** (repository Settings → Environments). Require at least one trusted reviewer, disable administrator bypass, restrict deployments to branch `main`, and protect workflow/migration changes with code review. Only put production credentials in this environment, **not** repository-wide secrets. Dispatch alone is not approval: the workflow also checks GitHub's approval history before obtaining database credentials. If environment reviews aren't supported/enabled, production deployment must not proceed.
3. Configure these **environment** values before dispatching:

| Kind | Name | Purpose |
| --- | --- | --- |
| Variable | `SUPABASE_PROJECT_REF` | Exact intended project ref; used to bind DB and Auth targets |
| Secret | `SUPABASE_DB_URL` | CI only: percent-encoded `postgres` password in the dedicated direct or session-pooler PostgreSQL DSN from Connect, database `postgres`, port 5432, append `?sslmode=require` (or `verify-full` with a trusted root). No transaction pooler. Not a Vercel/browser variable. The CLI authenticates directly with this DSN, not a personal management token. |
| Secret | `SUPABASE_PUBLISHABLE_KEY` | Public API probe using this project's publishable (or legacy anon) key |
| Secret | `SUPABASE_SERVICE_ROLE_KEY` | Trusted owner-provisioning step only; never prefix with `NEXT_PUBLIC_` |
| Optional variables | `CGS_OWNER_EMAIL`, `CGS_OWNER_UID` | Default approved pair: `cyphergreensystemsfirm@gmail.com` and `92277333-9bce-4d73-b7c8-c0c32688dd99`. A different pair requires operator verification and reviewer approval. |
| Optional secret | `CGS_INITIAL_PASSWORD` | Only for explicit first-time creation; generate a new unique password (20+ characters), never use a password shared in chat. Remove after bootstrap. |

## Deploy and verify

After merge, open **Actions → CGS database migrations → Run workflow**, select **main**, then review the target and approve the pending environment deployment. Validation first migrates a disposable Supabase instance and tests its real Auth and Data API. The production job checks the target DSN and migration history, runs `db push --dry-run`, applies pending versions with the CLI, verifies RLS/privileges/storage, probes all public content resources and finally verifies/provisions the owner. Regular Vercel builds, PRs and pushes cannot run the production job. No production reset, automatic migration-history repair, staff password reset or automatic rollback is performed.

- **Existing Auth account (default):** the Admin API must return the exact pinned ID with the expected confirmed email and no active ban. A mismatch or unknown ID stops provisioning. Existing credentials are never updated. If this exact user already has a lesser staff role, only approve `allow_promotion` after checking the identity and confirming this is the initial owner.
- **No existing Auth account:** explicitly set `CGS_OWNER_UID=new`, supply the one-time password secret and approve `allow_create`. `createUser` must succeed; a duplicate email is never adopted automatically. The script prints the new UID; pin it for subsequent runs. If Auth creation succeeds but the DB step fails, the new account has no staff privileges: pin and verify its UID, then retry. Do not delete an existing account to make this path succeed.
- The service-only grant takes a database lock, rechecks `auth.users` in the same transaction as the profile write, and records a private one-time receipt. A rerun checks the same identity and existing grant, not a blanket upsert. A demoted/deactivated bootstrap owner is **not** elevated again. Use an existing authorised super administrator for subsequent staff management. Deactivate staff in **User access**: deleting their profile revokes workspace/RLS access without deleting their Auth identity or content. No one can change their own role via the Data API.
- **Existing legacy database with no matching CLI history:** the fresh baseline fails closed; never clear tables to get past this check. Back up, inspect `check-production.sql`, compare the full schema (constraints, functions, grants, policies, triggers and storage) against version `20261125000100`. On a staging clone reconcile confirmed drift with reviewed additive SQL. Only after an independently reviewed exact match use CLI `migration repair <version> --status applied` for that already-installed version. Review the legacy seed separately: mark `20261125000200` applied if previously installed or the owner intentionally retired catalogue entries; do not reinsert retired content blindly. Never mark the hardening migration applied without actually installing it. Test pending migrations on the clone before approving production. Unrelated/partial schemas require manual review, not automatic adoption.

The application still uses `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (or existing supported aliases), `NEXT_PUBLIC_SITE_URL`, and a **server-only** service-role key for privileged API actions. Set these in the intended Vercel environment and redeploy after changing public settings. Verify `/sitemap.xml`, a published detail page, then `/techy/login`, authenticated dashboard, reload, logout and denial of subsequent access.

## Staff permissions

| Role | Scope |
|---|---|
| Super Administrator | All modules, including staff account creation and role assignment |
| Administrator | All catalogue, intake, media, settings and audit modules; no role management |
| Content Manager | Divisions, industries, services, products, projects, cases, vacancies, publications and media; no applications or inquiries |
| Project Manager | Projects, case studies, partnership proposals and media |
| Editor | Publications and media |

RLS is the enforcement boundary, independent of menu visibility. Public visitors can read published catalogue rows and public website settings. Never store secrets in website settings. Intake inserts are **not granted to anonymous or ordinary authenticated clients**. The validated Next.js endpoints store submissions with a server-only client, check shared database rate-limit windows and optionally notify staff. Notifications contain no submission text. Configure trusted forwarding headers at your deployment edge; never expose the origin behind an untrusted proxy.

Only authorised staff can upload JPEG, PNG or PDF files up to 4 MB; the server checks size, MIME and signatures and uses generated object paths. The `media` bucket is public: use it only for approved public material, never applicant CVs or private evidence. Copy the media URL into a platform screenshot list or publication document field. Use the Auth dashboard for recovery and account deactivation, configure backups and monitor storage, rate limits and email delivery.

## Production incident checklist (no database credentials in chat or Git)

1. In **the Vercel project that owns the live domain**, check Settings → Git → Production Branch (`main`), the deployment SHA, and **Production** environment scope. The other Vercel project and Preview scope have independent variables. Set `NEXT_PUBLIC_SITE_URL` to the actual absolute HTTPS site origin, and the public URL + publishable key from the **same corporate** Supabase project. Redeploy a new build after changing these. Never use a Postgres connection string, a REST URL ending `/rest/v1`, or a secret key for browser configuration. No `DATABASE_URL` is used.
2. With those environment variables available in a trusted local shell (or `.env.local`), run `npm run supabase:check` using Node 22.18+. Compare the reported host with the project in Supabase Dashboard. This is a read-only public-key probe: no profile reads, passwords, returned values or keys are printed. It checks all nine resources with their expected columns, the case-study relation, and the email provider setting. Zero visible rows is not a connectivity error and is not proof a policy is correct.
3. Interpret the HTTP status and machine code before changing SQL. HTTP 0: network/DNS/timeout or malformed settings. 401: check key, URL pairing and project status. `PGRST205`/`42P01`: missing or unexposed table/schema or stale schema cache. `42703`/`PGRST204`: missing column. `PGRST200`: missing/unrecognized relationship. `42501`: check grants **and** policies. Confirm the **Data API is enabled** and `public` is exposed. The public error boundary shows a non-sensitive reference: `CMS-CONFIG` (missing/invalid client configuration), `CMS-KEY` (401), `CMS-RELATION` (unknown table), `CMS-SCHEMA` (unknown column/relation), `CMS-PERMISSION` (42501), `CMS-ACCESS` (403 or schema exposure), `CMS-CONNECTION` (no HTTP response), or `CMS-UPSTREAM` (other). Use the matching server log entry for the exact operation/code. These are possible causes, not conclusions based on a failed build alone.
4. Run **`supabase/check-production.sql`** in the intended project's SQL editor. Compare the tables, columns, SELECT grants, RLS and policy expressions with `schema.sql`. On a verified new dedicated database, use the approved migration workflow above. On an existing or partial installation, **do not replay the baseline, disable RLS, overwrite records or grant anonymous writes**. Back up and prepare a reviewed additive migration against the specific differences found. If the inventory confirms **only public read grants are missing**, review `repairs/restore-public-select.sql`; it reapplies SELECT and schema USAGE transactionally, checks the expected RLS policy first and refuses an incompatible baseline. Missing policies or other drift need a schema-specific migration. No database migrations run during website builds.
5. In Auth settings enable email/password, disable public signup, confirm the approved user and their matching `profiles.id` and role. Set the Auth Site URL to the actual production origin and limit allowed redirects to approved URLs. This app uses password sign-in with SSR session cookies and relative redirects (`/techy/login` → `/techy/dashboard`); it does not use OAuth or require a callback route. Test on the live domain: sign in, reload a permitted module, try a forbidden module with a limited role, sign out, then revisit `/techy/dashboard` and confirm the login redirect. Do not supply administrator credentials in an issue or chat.
6. Verify `/sitemap.xml` and a published detail URL on the intended deployment. Public layout and sitemap read at **request time**; the root 404 uses static default metadata. Only unconfigured non-production previews use the bundled catalogue. In a connected deployment primary directory failures reach the error boundary, optional sections omit unavailable rows, and the sitemap does not invent URLs for unreadable collections. Server logs include only resource, HTTP status and a sanitized code. A green build is not proof that live reads or staff access succeeded.
